# Code Review 工作流

按以下顺序执行、每步都要明确告诉用户你在做什么：

## Step 1：明确审查范围

先用 `bash` 跑 `git status` 看有哪些改动、`git diff` 看具体内容。

如果用户没指定分支、默认审 vs `main` 的 diff。

## Step 2：读项目约束

`read_file CLAUDE.md` —— 看项目有没有硬性规则（比如"CDN 必须锁精确版本"、"不允许写 app/index.html"）。

如果 rag_search 可用、检索"代码规范"相关的文档补充上下文。

## Step 3：逐文件检查

按 diff 里的顺序、对每个改动文件：

- **正确性**：逻辑有没有 bug、边界 case 有没有漏
- **安全性**：外部输入有没有校验、有没有 SQL 注入 / XSS / 命令注入风险
- **一致性**：跟项目其他代码风格是否一致（先 grep 看现有 pattern）
- **测试覆盖**：有没有配套测试

**每发现一个问题都要具体到 file:line**、别泛泛而谈。

## Step 4：输出报告

按下面模板输出：

```
## Review 报告

### 🔴 必须修（阻塞合并）
- <file:line> <问题描述> <建议修法>

### 🟡 建议改（不阻塞）
- <file:line> <问题描述>

### ✅ 做得好的
- <一两点值得肯定的地方——避免只有批评>

### 📊 总体评估
- <一句话结论：可以合 / 修完必须修的项后可合 / 需要重做>
```

## 关键原则

- **具体优于笼统**——"这里可能有 bug" 换成 "第 42 行的 divide 没检查 b==0、会抛 DivisionByZero"
- **有建议、别只批评**——每个问题给出至少一个修法
- **对好的也要说**——纯批评会让人抗拒接受反馈
